# fons-agentid-GPU

今天一个 agent 在链上就是一个 EOA：**一条 nonce 队列**，所有市场排一条线；**一把私钥**，所有资金一个爆炸半径。

- **票据找零账户** —— 把一份余额切成 N 张互不重叠、有上限、会过期的支出承诺。
  **切开 agent 的安全边界**：被盗上限从「全部身家」变成「一张票」。
- **ERC-4337 二维 nonce 车道** —— 让这些承诺各走各的通道。
  **绕开 EOA 单条 nonce 队列的队头阻塞**：一笔卡住只堵自己那条。

GPU 的本事不是单核更快，是通道多、互不阻塞、各自失败。我们给 agent 的链上执行做的就是这件事。

> 说明：链上**执行**仍然是串行的，这套东西不加快单笔交易。它消掉的是**队头阻塞和故障连带**。

## 调度器：两张表必须分开

这是整套东西唯一真正承重的工程决定。

| 表 | 只回答 | 什么时候释放 |
| --- | --- | --- |
| **车道表** `scheduler/src/lanes.ts` | 这条车道上有没有一笔**还没落地的交易** | 交易落地那一刻 |
| **业务表** `scheduler/src/rounds.ts` | 这一轮生意**走到哪了** | 生意真的做完 |

混成一张就会出这种事：第五类（身份门禁类）的一轮在等用户去 agent 对话框点确认，
可能等 48 小时；如果那条车道一直被它占着，Pancake 的单子就会因为「没有空车道」
排在后面 —— **一个毫无关系的人工确认，堵住了一个本该并行的市场**。

所以 `onConfirm()` 的含义严格是「这笔交易上链了」，**不是**「这一轮做完了」。
业务表里干脆**没有** `onchain` 这个状态 —— 留着它只会诱导人把两件事混起来。

### 另外两条不许动的规矩

**本地不许缓存 nonce 的 seq，每次发送前现问 `getNonce`。**
UserOp 被 bundler 丢掉时那个 seq **没有被消耗**；本地自增就会在这条车道上留一个
空洞，而 4337 跟 EOA 一样不接受空洞 —— 后面所有单子全部卡死，而且补不回来。

**卡住的车道不自动释放，只能同 nonce 提价重发。**
那笔可能下一秒就落地；车道一还出去，新单子会拿到同一个 seq，两笔互相顶，
结果取决于 gas 高低。重发到上限还不动，就发一笔注定 revert 的空操作把这个 seq
消耗掉（4337 的 nonce 在验签阶段就递增，执行 revert 不会退回来）。

### 第五类的闸

⑤ 的 mint 是 **AgentID EOA 自己发交易**，而那个地址只有一条 nonce 队列、
**由币安 MPC 管** —— 我们既填不了空洞也催不快。这一类的并行度就是 1。

调度器从花票发出去那一刻起持闸，一直持到回扫落地，同一时刻只放一轮。
原因不只是 nonce：这段时间里钱在 AgentID EOA 上，**票据的「最多亏 N」保证是失效的**，
所以要把这个窗口压到最小。

界面上第五类在任何状态下都**不许显示成「并行」**，如实写
「排队中 · 等你在 agent 对话框确认」。这条有测试盯着。

## 权限披露

> 下面每一行都是从**链上部署的字节码**读出来的（`forge inspect methodIdentifiers`
> 对着源码逐个核的），不是从文档抄的。合约**不可升级**（EIP-1167 代理焊死实现），
> 所以这份清单就是全部，以后也不会多出来。

### 一句话

**平台对用户的资金零权力。** 工厂里一个管理员函数都没有，账户里也没有任何
「平台」角色。部署钥匙部署完就是**一张付过的 gas 车票**，再也动不了任何东西。

下面说的 `owner`，是**用户自己的冷钱包**，不是我们。

### 三把钥匙能做什么

| 钥匙 | 是谁的 | 能做 |
| --- | --- | --- |
| **`owner`** | **用户自己的冷钱包** | 开票 · 撤票 · 回收 · 一键作废 · 换 agent 密钥 · 转移 owner · 提款（三种） |
| **`agentKey`** | skill 在用户机器上生成，私钥不出机器 | 花票 · 按票付款 · 卖回 · 回收过期票 · 把钱拉回账户 |
| **`agentIdEoa`** | 用户的币安 Agentic Wallet | **什么都不能做** —— 只读身份锚，有测试钉着 |

### 逐个函数

**只有 `owner` 能调（9 个）**

| 函数 | 做什么 | 能不能动钱 |
| --- | --- | --- |
| `issueBatch` | 开票 | 不动，只是把余额标成「已承诺」 |
| `cancel` / `cancelBatch` | 撤票 | 不动，把没花的额度还回可用 |
| `bumpEpoch` | **一键作废全部票** | 不动。恐慌按钮，一行 `epoch++` |
| `rotateAgentKey` | 换 agent 密钥 | 不动 |
| `transferOwner` | 转移 owner | 不动，但**转走之后旧 owner 就没权限了** |
| `withdraw(asset,to,amount)` | **提走 ERC20** | ✅ **能**，但受 `available` 限制 —— 已承诺的部分提不走 |
| `withdrawNative(to,amount)` | **提走原生 BNB** | ✅ **能**，不受限（原生币不进票据账） |
| `withdrawDeposit(to,amount)` | 提走 EntryPoint 里的 gas 存款 | ✅ **能** |

**只有 `agentKey` 能调（1 个）**

| 函数 | 做什么 | 上限 |
| --- | --- | --- |
| `payout(noteId,amount)` | 按票把钱转给票上钉死的收款人 | 票面封死 |

**`agentKey` 或 EntryPoint 能调（3 个）**

| 函数 | 做什么 | 上限 |
| --- | --- | --- |
| `spend` / `execute` | 花票：approve 给票上钉死的 market 并调它 | 票面封死；`requireReturn` 开着时**买到的必须回账户** |
| `sellInto` | 把持有的币卖回票的计价资产 | market 钉死；**卖出后计价资产必须增加**，否则 revert |

**`agentKey` / `owner` / EntryPoint 都能调（2 个）**

| 函数 | 做什么 |
| --- | --- |
| `reclaim(ids)` | 回收过期票的额度（只减不增，谁调都一样） |
| `sweep(asset,from)` | 把钱从 AgentID 钱包**拉回账户** —— 方向是往里拉，拉进来就归 `owner` 管 |

**谁都能调（无权限，7 个只读 + 2 个）**

`owner()` `agentKey()` `agentIdEoa()` `agentId()` `epoch()` `notes()` `reserved()`
`available()` `noteIdOf()` 全是只读。另外两个：

- `addDeposit()` —— 任何人都能**往里充** gas，没有危害
- `validateUserOp()` —— **只有 EntryPoint 能调**，而且它只认 `agentKey` 的签名
- `initialize()` —— 工厂部署时调一次，`owner != 0` 之后再调直接 revert

### 没有的东西

明确说清楚，因为这几条是常见的 rug 手法：

| | |
| --- | --- |
| 可增发 | ❌ 这不是代币合约 |
| 改税率 / 手续费 | ❌ **合约里一处收费机制都没有**（搜 fee / treasury / 抽成，零命中） |
| 暂停交易 | ❌ 没有 `pause`。唯一能停的是 `owner` 自己按 `bumpEpoch` 作废自己的票 |
| 冻结用户资产 | ❌ 没有黑名单、没有冻结 |
| 平台提走用户资产 | ❌ **没有任何平台角色**。能提款的只有 `owner`，那是用户自己的冷钱包 |
| 合约可升级 | ❌ EIP-1167 代理**焊死**实现地址。要改只能部新工厂，**老账户永远跑老版本** |
| 代理管理员 / `upgradeTo` | ❌ 最小代理没有管理槽 |

### 主网实证（2026-11-24）

下面这些不是「测试里绿着」，是在 BSC 主网拿真钱跑过的：

| 做了什么 | 结果 |
| --- | --- |
| `bumpEpoch` 恐慌按钮 | 3 张票锁着 2.3 USDT → 一笔交易全释放，**gas 50,315，和票数无关** |
| | 票本身**一张都没改**（`closed` 仍是 false），只是留在旧 epoch 上自动失效 |
| `withdraw` 超过可用 | ✗ `OverBudget` —— 已承诺的钱提不走 |
| `withdraw` 可用范围内 | ✓ 到账 |
| `withdrawNative` 被 `agentKey` 调 | ✗ `NotOwner` |
| `withdrawNative` 被 `owner` 调 | ✓ 原生 BNB 取回（**v5 才有，v4 及以前进去就出不来**） |
| `withdrawDeposit` | ✓ gas 存款取回 |
| `reclaim` 过期票 | ✓ 可用 +1.3975，`reserved` 归零，票关闭 |
| `reclaim` 额度用尽但没到期的票 | ✗ `NoteNotExpired` —— **它只收到期的** |

`rotateAgentKey` / `transferOwner` 也验了：

| 做了什么 | 结果 |
| --- | --- |
| `rotateAgentKey` 换成新地址 | ✓ 链上立刻改。**旧密钥签的 UserOp 当场被拒**，新密钥当场可用 |
| `transferOwner` 转给临时地址 | ✓ 转完**旧 owner 连恐慌按钮都按不了**（`NotOwner`） |
| 临时 owner 转回来 | ✓ 权限真的跟着 owner 走，不是摆设 |

⚠️ **换密钥之后 skill 不会自己知道。** 旧私钥签的 UserOp 会被
`validateUserOp` 判成签名无效，bundler 直接拒收，而且**错误里不会提示
「你该换密钥了」** —— 看起来就是「莫名其妙发不出去」。所以加了
`gpu.mjs rekey`：读链上认哪把、和本地比、不一致就说清楚怎么办。

**多车道并行（这是整个产品的核心卖点，2026-11-24 第一次在主网证明）**：
一次 `tick` 把三轮同时发出去，分在三条车道上。

| | nonce | 落在哪块 | 哪把 bundler 钥匙发的 |
| --- | --- | --- | --- |
| 车道 0 | `9` = `0<<64 \| 9` | 135411263 | `0x48C33F57…` |
| 车道 1 | `18446744073709551616` = `1<<64 \| 0` | 135411276 | `0x351f9fbE…` |
| 车道 2 | `36893488147419103232` = `2<<64 \| 0` | 135411289 | `0x2570d90E…` |

并发之后各车道的 seq：`0 → 10`、`0 → 1`、`0 → 1` —— **各自独立计数**。

两层并行都在起作用：**账户内部**靠二维 nonce（车道各走各的 seq），
**我们的发送侧**靠三把 bundler 钥匙（各自一条 EOA 队列）。
只有一条车道的话，这三笔必须严格排队 —— 第一笔不落地，后两笔连发都发不出去。

顺带：身份类那一轮落地后进「等你在 agent 对话框确认」，**车道 2 当即还了出来** ——
「等人确认的那一轮不占车道」这条在并发场景下也成立。

**恐慌按钮为什么是固定 gas**：它只做一件事 `epoch++`。票不是被逐张关掉的，
是整代作废。票最多的时候正是最该按的时候 —— 遍历方案在那时会 gas 爆炸，这个不会。

### ❗ agentKey 被拿走会怎样 —— 最直接的那个问题

2026-11-24 用 `eth_call` 在主网账户上逐条模拟过，**不是推演**。

#### 它做不到的

| 想干什么 | 结果 |
| --- | --- |
| 自己开一张票（凭空造预算） | `NotOwner` |
| 换掉 agentKey（锁死主人） | `NotOwner` |
| 改 owner（夺走账户） | `NotOwner` |
| 提走账户里的 BNB | `NotOwner` |
| 按恐慌按钮（捣乱） | `NotOwner` |
| 撤掉主人开的票 | `NotOwner` |

**最要紧的是第一条：它开不了票，所以造不出新预算。** 账户里没开票的钱，它一分都碰不到。

#### 它能做的，只在主人已经开出的票里

```solidity
payout(bytes32 noteId, uint128 amount)
       ↑ 没有收款人参数 —— 收款人恒等于票上的 market
```

**agent 填不了别的地址。** `spend` 同理 —— `market` 钉死在票上，只能调那一个合约。

#### 但不是所有票都一样安全

```
① 交易票  requireReturn=true
          买到的东西必须回账户，agent 送不出去
          最坏：买了垃圾币（策略问题，不是安全问题）

②③ 入金票 requireReturn=false 且 dataHash=0
          calldata 自由。如果 market 是那种「能指定收款人」的合约，
          **agent 能把 ≤ 票面的钱导到别处**
```

这就是 2026-11-24 抓到并用 `dataHash` 堵的那个洞。但 **`dataHash = 0` 是允许的** ——
填不填在开票人手里。

**所以规矩是：入金型票必须钉 `dataHash`。** skill 里写了，`spend` 命令会预检，
**但合约不强制** —— 这是刻意的，① 的交易票参数随行情变，钉死就没法交易了。

#### 最坏情况

```
agentKey 被拿走  →  最多损失「所有活着的票还没花完的部分」
                    而且每一笔都只能流向票上写死的那个地方
主人能做什么     →  bumpEpoch 一笔交易作废全部票（实测 gas 50,315）
                    rotateAgentKey 换掉那把钥匙
没开票的钱       →  一分都动不了
```

对比一下「agent 就是账户本人」那种模型：钥匙没了，**账户里的钱全暴露**。

### 已知的残余风险（不是 bug，说清楚）

1. **`owner` 权力很大** —— 它能提走全部可用余额、作废全部票、转移 owner。
   **这是设计** —— 那是用户自己的钱和自己的钥匙。但这也意味着
   **`owner` 私钥丢了，这个账户就没救了**（没有社恢、没有平台后门，我们想帮也帮不了）。
2. **票保证的是「≤ 票面的钱会离开账户」，不是「买到的东西会回来」。**
   `requireReturn` 开着能强制输出回账户，但**管不了价格** —— agent 照样能买垃圾币。
3. **第五类（身份类）的票是毛流出上限。** 钱转去 AgentID 钱包之后票就管不着了，
   `sweep` 回来**不冲减** `netOut`。所以这类票要按轮开、开小额。
4. **接入码泄漏能被抢注。** 后果是**抢占地址 + 归属被污染**，不是丢钱（那个账户里
   本来就没钱）。换一把 `agentKey` 就换一个地址，照样开得出户。缓解靠 deadline（默认 10 分钟）。

### 安全约束（我们给自己定的）

- **网页永远不做扫码登录 Agentic Wallet。** 登录只能由用户在自己机器上用币安官方 CLI 完成，
  我们不碰、不存、不代持会话。
- **授权按币种、按额度**，默认只授这一轮要拉回来的那笔，**绝不索取无限额授权**。
- **gas 费不由平台出** —— bundler 垫付，EntryPoint 从用户的 gas 存款退回。
